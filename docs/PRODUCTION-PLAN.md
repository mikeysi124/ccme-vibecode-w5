# ถ้าจะใช้จริงต้องเปลี่ยนอะไร

เวอร์ชัน 1.3.1 เป็นโปรโตไทป์ระดับข้อมูลที่ 1 ตามสไลด์วิชา 7: ข้อมูลสมมติ 100% วางบนบริการสาธารณะได้ · เอกสารนี้เขียนตามข้อเสนอของเพื่อนร่วมรุ่นว่า ถ้าวันหนึ่งมีทรัพยากรครบ ต้องปรับอะไรบ้างจึงจะเป็นระบบระดับ production

## 1. เส้นทางจากโปรโตไทป์สู่ของจริง

| เรื่อง | ตอนนี้ 1.3.1 | ถ้าจะใช้จริง | ใครทำ / เงื่อนไข |
|---|---|---|---|
| ข้อมูล | สมมติ 100% | นำร่อง: ข้อมูลจริงที่ตัดตัวระบุแล้ว · ใช้จริง: ข้อมูลที่ระบุตัวบุคคลได้ | ระดับ 2 ต้องผ่านฝ่าย IT และมีสัญญาประมวลผลข้อมูล · ระดับ 3 ต้องผ่านคณะกรรมการสารสนเทศ มีผู้รับผิดชอบข้อมูล และควรอยู่ในประเทศไทย |
| ที่อยู่ระบบ | หน้าเว็บบน GitHub Pages · ฐานข้อมูล Supabase แบบฟรี ภูมิภาค Singapore | server ของโรงพยาบาล หรือ GDCC หรือผู้ให้บริการคลาวด์ในไทย | ฝ่าย IT · ผู้พัฒนาเตรียม 4 เรื่องไปคุย: ลิงก์ที่ใช้ได้จริง · เก็บอะไรและใครเข้าถึง · ผู้ใช้กี่คนใช้บ่อยแค่ไหน · ใครเป็นเจ้าของหลังส่งมอบ |
| การเข้าสู่ระบบ | อีเมล + รหัสผ่าน ยืนยันอีเมลก่อนใช้ | MFA หรือ SSO ของโรงพยาบาล หรือ ThaID | Supabase Auth รองรับ MFA แบบ TOTP · ThaID ต้องตรวจเงื่อนไขการเชื่อมต่อก่อน |
| สิทธิ์ | RLS ทุกตาราง + บทบาทในตาราง `profiles` · 23 ก.ย. Codex พบว่า policy ของ `profiles` `cases` และ `overrides` ต้องเข้มขึ้นสำหรับผู้ที่ล็อกอิน → รัน `supabase-w7-hardening.sql` แล้ว ทดสอบผ่าน 5 ข้อ | เพิ่มการทบทวนสิทธิ์เป็นรอบ และถอนสิทธิ์เมื่อย้ายหน่วยงาน | หัวหน้าหน่วย + IT |
| การแจ้งและความยินยอม | แจ้งข้อมูลที่เก็บ + แบบขอความยินยอม v1.0 ก่อนล็อกอิน · เก็บค่าล่าสุดและประวัติการให้/ถอน 10 ครั้งล่าสุดไว้ใน Auth metadata ของบัญชี ซึ่งผู้ใช้แก้เองได้และติดไปใน JWT จึงเก็บยาวไม่ได้ · กั้นที่ฝั่งแอปและตรวจซ้ำก่อนบันทึกเคส · บันทึกจากหลายแท็บพร้อมกันยังเขียนทับกันได้ | ตารางความยินยอมที่เพิ่มได้อย่างเดียว และให้ฐานข้อมูลตรวจความยินยอมก่อนรับเคส · ผู้ป่วยได้รับแจ้งตามนโยบายของโรงพยาบาล | การรักษาพยาบาลใช้ฐานทางกฎหมายตาม ม.26 ได้โดยไม่ต้องขอความยินยอม แต่ต้องแจ้งเสมอ |
| สำรองข้อมูล | ยังไม่ได้ตั้ง | สำรองอัตโนมัติ และลองกู้คืนจริงอย่างน้อยปีละครั้ง | IT |
| ความต่อเนื่อง | แพ็กเกจฟรีหยุดเองเมื่อไม่มีการใช้งาน 7 วัน | แพ็กเกจเสียเงิน หรือฐานข้อมูลในโรงพยาบาล | ค่าใช้จ่ายรายเดือน ต้องตั้งงบ |
| บันทึกการใช้งาน | บันทึกผู้บันทึก เวลา และการ override | บันทึกการเปิดอ่านด้วย และเก็บตามระยะเวชระเบียน | IT + เวชระเบียน |
| เหตุข้อมูลรั่ว | ปิดการเข้าถึงและหมุนกุญแจ ตามนโยบาย v1.0 | แผนตอบสนองเป็นลายลักษณ์อักษร · แจ้งสำนักงานคณะกรรมการคุ้มครองข้อมูลส่วนบุคคลโดยไม่ชักช้าภายใน 72 ชั่วโมงนับแต่ทราบเหตุเท่าที่ทำได้ เว้นแต่ไม่มีความเสี่ยงต่อสิทธิและเสรีภาพ · ถ้าเสี่ยงสูงแจ้งเจ้าของข้อมูลพร้อมแนวทางเยียวยาด้วย ตาม ม.37(4) | ผู้ควบคุมข้อมูลของโรงพยาบาล |
| ความถูกต้องทางคลินิก | ชุดตรวจ 77 ข้อ = เคสที่รู้คำตอบ 34 เคส + ตรวจตรรกะ 43 ข้อ | UAT กับพยาบาลคัดกรอง ≥3 คน วัดเวลาต่อรายและอัตรา override · เทียบกับผู้เชี่ยวชาญ | ถ้าเก็บข้อมูลเพื่อวิจัย ต้องผ่านคณะกรรมการจริยธรรมก่อน |
| เชื่อมระบบโรงพยาบาล | ไม่เชื่อม HIS | รับส่งข้อมูลผ่านมาตรฐาน เช่น HL7 FHIR | IT + ผู้ให้บริการ HIS |

## 2. ความเสี่ยงของแพลตฟอร์ม

เพื่อนร่วมรุ่นเตือนว่าบริการใหญ่ก็หยุดได้ · ตรวจจากต้นทางแล้ว: GitHub รายงานเหตุขัดข้อง 5 ครั้งในเดือนสิงหาคม 2026 · 6 ส.ค. เหตุการณ์ยาว 10 ชั่วโมง 42 นาที ผลกระทบราว 9 ชั่วโมง รวมถึงการ build ของ GitHub Pages · สาเหตุที่ GitHub ระบุคือรองรับโหลดไม่พอและปัญหาของผู้ให้บริการต่อ ไม่มีครั้งไหนระบุว่าถูกโจมตี ([GitHub availability report](https://github.blog/news-insights/company-news/github-availability-report-august-2026/)) · หน้าประกาศสำหรับนักพัฒนาของ LINE แจ้งระบบขัดข้อง 9 ครั้งในปี 2026 นับถึง 23 ก.ย. ([LINE Developers](https://developers.line.biz/en/news/2026/))

| เหตุ | ผลต่อแอปนี้ | ตอนนี้รับมืออย่างไร | ถ้าจะใช้จริง |
|---|---|---|---|
| GitHub ขัดข้อง | build และ deploy ใหม่ไม่ได้ ถ้าล่มหนักหน้าเว็บอาจเข้าไม่ได้ | มีสำเนาโค้ดครบในเครื่องผู้พัฒนา · หน้าเว็บเป็นไฟล์ static ย้ายไปวางที่อื่นได้ทันที | เตรียมลิงก์สำรองบนอีกแพลตฟอร์ม เช่น Cloudflare Pages ที่ชี้ไฟล์ชุดเดียวกัน |
| Supabase ขัดข้องหรือหยุดเพราะไม่มีการใช้งาน | ประเมินยังทำได้เพราะ engine ทำงานในเบราว์เซอร์ แต่บันทึกลงฐานข้อมูลไม่ได้ | เปิดหน้าใหม่ ถ้าแอปดึงข้อมูลบัญชีไม่ได้จะกลับไปเก็บในเครื่องเอง · ใช้งานสม่ำเสมอก่อนช่วงที่มีคนต้องใช้ | แพ็กเกจเสียเงินหรือฐานข้อมูลในโรงพยาบาล + สำรองข้อมูล |
| CDN ที่โหลด supabase-js ขัดข้อง | ต่อฐานข้อมูลไม่ได้ | แอปกลับไปโหมดเก็บในเครื่องเองเพราะตรวจไม่พบ client | วางไลบรารีไว้กับหน้าเว็บเอง ไม่พึ่ง CDN |
| LINE ขัดข้อง | แอปนี้ไม่ใช้ LINE | — | ถ้าอนาคตเชื่อม LINE Official Account ต้องมีช่องทางหลักอื่นที่ไม่พึ่ง LINE |
| ผู้ให้บริการเปลี่ยนเงื่อนไขหรือราคา | อาจต้องย้ายระบบ | โครงสร้างฐานข้อมูลเป็น SQL มาตรฐานใน `supabase-schema.sql` ย้ายไป PostgreSQL ที่อื่นได้ | ระบุแผนย้ายออกไว้ในสัญญา |

## 4. เรื่องที่โปรโตไทป์นี้ตั้งใจไม่ทำ
- ไม่เก็บชื่อ HN เลขบัตร หรือวันเกิดของผู้ป่วยตั้งแต่ระดับโครงสร้างตาราง
- ไม่เรียกโมเดล AI จึงไม่มีข้อมูลออกไปยังผู้ให้บริการ AI · ถ้าจะเพิ่ม ห้ามใช้ API แบบฟรีกับข้อมูลผู้ป่วย เพราะเงื่อนไขของ Gemini API แบบไม่เสียเงินระบุว่านำข้อมูลไปปรับปรุงบริการได้และมีคนอ่านได้ ([Gemini API terms](https://ai.google.dev/gemini-api/terms))
- ไม่ตัดสินแทนพยาบาล ระบบเสนอ พยาบาลตัดสิน
